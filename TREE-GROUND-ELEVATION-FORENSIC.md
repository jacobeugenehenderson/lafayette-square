## The two elevation artifacts (the load-bearing fact)

There are **TWO separate elevation sources**, and the float lives in how they relate:

1. **`public/baked/<look>/ground.{bin,json}`** — the per-look ground **MESH**. Baked **~FLAT** (measured: vertex Y max **4.4 cm**; bbox Y min=max=0). Baked by `cartograph/bake-ground.js`. *Jacob rebaked this 06-24 (the ground tri-cut / elevation work — the modified `ground.*` files).*
2. **`src/data/terrain.{json,bin}`** — the **GLOBAL, build-time** heightmap (a 421×421 raw Float32 grid). This is the elevation the runtime GPU-displacement samples for **everything**. mtime **2026-05-13** (stable, unchanged for >1 month; NOT regenerated by the ground rebake).

The ground mesh is flat on disk; **real hills/valleys are applied at render time** by sampling `terrain.bin` × `uExag`. So "the elevation layer that isn't 0,0" = the runtime terrain displacement, sourced from `src/data/terrain.bin`.

**Bounds match exactly:** `terrain.json` bounds `{minX:-1065,maxX:1035,minZ:-1065,maxZ:1035}` == `ground.json` bbox `{min:[-1065,..],max:[1035,..]}`. So the ground mesh and the heightmap share one coordinate frame.

## The runtime displacement chain (verified, file:line)

- `src/utils/terrainShader.js`
  - `:36` loads `terrain.bin` → singleton **`terrainTexture`** (`RedFormat`, `.r` = meters above local-min, ≥0).
  - `:59` **`terrainExag = { value: 0 }`** — the shared exaggeration uniform (`uExag`), mutated per-view. **Hero = `V_EXAG`** (`:16,20` — "dramatic telephoto terrain"). **Canonical `V_EXAG = 1.5`** lives in `src/lib/terrainCommon.js:18`; terrainShader re-exports it (`:29`). ⚠️ the `:20` comment "currently 1.8" is STALE — the imported value is 1.5.
  - `:63-70` shared `UNIFORMS` (uTerrainMap, uBMinX/Z, uSpanX/Z, uExag) — **every** terrain-patched material gets the SAME objects via `assignTerrainUniforms` (`:73`).
  - `:195` **`TERRAIN_DISPLACE_INSTANCED`** — samples at the instance origin (`modelMatrix*instanceMatrix*0`), lifts the whole instance: `transformed.y += texture2D(uTerrainMap,_tuv).r * uExag / instYScale`. `instYScale` = length of `instanceMatrix[1]` (so the lift lands as `sample*uExag` world meters after instance scaling).
  - `:217` **`patchTerrainInstanced(mat)`** — the helper that wires the above onto a material.
- **Ground** uses per-vertex displacement (each ground vertex samples at its own XZ). **Buildings** use `patchTerrainAtCentroidRaw` (footprint centroid). **Lamps** use `patchTerrainInstanced`. → all lift from the same heightmap.
- **Trees DO follow terrain:** `src/components/treeAtlasMaterial.js:777` **`patchTerrainInstanced(treeMaterial)`** — chained AFTER sway/deformer (comment `:774`; the snippet re-inserts `#include <begin_vertex>` so the prior `.replace` still finds it). So in principle a tree lifts by the heightmap value at its trunk XZ — exactly what the ground lifts there → trunk base should sit on the ground.
- **Salon preview material SKIPS the patch** (`treeAtlasMaterial.js:836,901`) — workstage is flat single-tree ground; correct, not a bug.
- `arborist/bake-trees.js:512` plants every tree instance at baked **`y=0`** ("Ground reverted to flat (#19); trees plant at y=0 + override"). The runtime terrain patch is the ONLY thing that lifts them onto the hills. **When the ground was flat (#19), y=0 was correct; Jacob re-introducing elevation is what exposed this.**

## What's VERIFIED vs OPEN

**Verified:**
- Baked tree GLBs all sit at `baseY=0.000` (measured, slab + source). No grounding bug in geometry.
- Baked ground mesh is ~flat (4 cm); elevation is runtime-only from `src/data/terrain.bin`.
- terrain.bin ↔ ground bounds match; both sample the same global May-13 heightmap.
- Trees ARE patched with `patchTerrainInstanced` (treeAtlasMaterial.js:777).

**Open hypotheses for the float (need the LIVE APP — proxy analysis is exhausted; operator's eye is the gate):**
1. **The `begin_vertex` replacement chain silently no-ops the terrain patch on the tree material.** sway → deformer → terrain all string-replace `#include <begin_vertex>`; if the literal include isn't present when `patchTerrainInstanced`'s replace runs, trees never lift → float at y=0 over the displaced ground. *Cheapest live check: in the running app, inspect the compiled tree vertex shader for the `uTerrainMap` sample, or temporarily set `terrainExag.value` and see if trees move with the ground.*
2. **`instYScale` ≠ 1** — if the per-instance matrix carries authored scale (it shouldn't; bake says "scale baked into GLB, runtime renders at scale=1"), the divide mis-scales the lift.
3. **Sign/anchor** — ground per-vertex vs tree instance-origin lift could diverge if the heightmap's local-min anchor differs from where the tree's y=0 sits.

## SSoT status of the elevation chain (Jacob's Q, 2026-06-25)

**The elevation DATA is already single-sourced.** `src/data/terrain.{json,bin}` is the ONE heightmap — runtime displacement (ground/buildings/lamps/trees) AND `bake-ground.js`'s tri-cut deviation test both read it. No duplicated elevation grid.

**What is NOT single-sourced (the real drift risk): the sampler + the `V_EXAG` constant.**
- `src/lib/terrainCommon.js` is the *designed* SSoT — "the math and constants live here once" — exporting `makeElevationSampler`, **`V_EXAG = 1.5`** (`:18`), `displaceGeometry`. Shared browser+node. The runtime imports it (`terrainShader.js:29`).
- BUT `cartograph/bake-ground.js` **re-rolls its own sampler** (`:92–115`) and **hardcodes `const V_EXAG = 1.5`** (`:101`) instead of importing terrainCommon. It matches today *by coincidence*; if terrainCommon's V_EXAG ever changes (the stale "1.8" comment shows it was contemplated), the ground mesh gets tri-cut-refined for the OLD exag while the runtime lifts by the NEW one → under-tessellated terrain / visible error where it curves.

**The SSoT fix (small, endorsed):** make `bake-ground.js` `import { makeElevationSampler, V_EXAG } from '../src/lib/terrainCommon.js'` and delete its hand-rolled `_terrainSampler` + hardcoded constant. Then ONE sampler + ONE `V_EXAG` spans bake + runtime, and the mesh auto-recalibrates to any exag change. (This is the memory-flagged "tri-cut coupling: import V_EXAG SSoT so the mesh auto-recalibrates.") ⚠️ Note this is about bake/runtime *consistency*, NOT the tree float — both ground and trees already use the runtime sampler for actual lift, so they agree on displacement regardless; the float is hypothesis 1 above.
