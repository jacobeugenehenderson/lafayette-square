## 1. The publish-loop pattern

The codebase is a **public-facing runtime app** plus a small set of **standalone helper apps**. Each helper authors a specific kind of content and publishes one canonical artifact. The runtime composes those artifacts into the rendered scene.

```
┌────────────────┐    publishes     ┌──────────────────────────────┐
│  Cartograph    │ ───────────────▶ │ public/baked/<id>/ground.bin │ ──┐
└────────────────┘                  │ + ground.json + lightmap.png │   │
                                    └──────────────────────────────┘   │
                                                                       │
┌────────────────┐    publishes     ┌──────────────────────────────┐   │   ┌──────────┐
│  Stage         │ ───────────────▶ │  scene.json (the slab)       │ ──┼──▶│ Runtime  │ ──▶ pixels
└────────────────┘                  └──────────────────────────────┘   │   └──────────┘
                                                                       │
┌────────────────┐    publishes     ┌──────────────────────────────┐   │
│  Arborist      │ ───────────────▶ │ public/trees/<species>/...   │ ──┤
│  (scaffold)    │                  └──────────────────────────────┘   │
└────────────────┘                                                     │
                                                                       │
┌────────────────┐    publishes     ┌──────────────────────────────┐   │
│  Meteorologist │ ───────────────▶ │ public/clouds/{presets,      │ ──┘
│ (standalone)   │                  │            almanac}.json     │
└────────────────┘                  └──────────────────────────────┘
```

**Note on Meteorologist's shape:** it shipped as a **standalone app** (`/meteorologist.html`), not a Stage panel — the earlier "authoring UI lives inside Stage" plan was not executed. The publish-loop pattern still holds; only the editor's housing differs. See [`../meteorologist/ARCHITECTURE.md`](../meteorologist/ARCHITECTURE.md). **Note on Stage's artifact:** the planned `stage-config.json` never materialized — every Stage channel folds **field-by-field into `scene.json`** (the slab); there is no separate stage-config layer (see `BAKE.md §5`, `DOC-CODE-COHERENCE.md` B1).

**Properties of this pattern, used everywhere:**

- **Helpers are decoupled.** Cartograph never imports Arborist's code; the runtime never imports a helper's editor surfaces. They only know about each other through the artifacts.
- **Artifacts are pristine.** No helper-specific scaffolding gets baked in. An artifact is a clean handoff format that any consumer (this app, a future kiosk, an embedded preview) can read without owning the producer.
- **Helpers are dev-time tools (v1).** They run locally. They're not deployed alongside the runtime. The deployed LS app has zero write paths back to a helper — the slab is consumed read-only as static files. *v2+ direction:* a hosted bake service with per-operator auth so non-maintainer operators can publish their own instances without git write access to the kit repo. Tracked in `cartograph/BACKLOG.md` "Hosted bake service with auth (v2+)".
- **One artifact per helper, per concern.** If you ever feel like a helper should publish two artifacts, that's usually two helpers.

When adding a new helper, follow this pattern verbatim: standalone editor app → one published artifact → runtime consumer that reads it. See `cartograph/README.md` for the established template.

## 2. Geometry vs. styling — the Designer / Stage split

Cartograph itself is internally split the same way the larger system is. Two roles, two tools, one app:

- **Designer = shape.** Survey, Measure, Plant *(future)*, centerlines, caps, anchors, boundary, tree positions. Geometry edits propagate to *every* Look.
- **Stage = look.** Color, visibility, materials, shaders, time-of-day. Per-Look styling.

This same split shows up in every helper that has both kinds of editing:

| Concern | Owner |
|---|---|
| Where the streets go | Cartograph Designer |
| What the asphalt is colored | Stage Surfaces (per Look) |
| Which trees stand at which positions | Cartograph Designer (Plant tool, v1.1) |
| What color sugar maples are | Stage Surfaces (per Look) |

**Looks vary styling, never shape.** That rule is what lets the runtime swap Looks at zero cost — just a different `design.json` (+ the baked `ground.json`/`ground.bin`), the geometry is identical. *(The per-Look runtime `ground.svg` was retired — `bake-svg.js` is demoted to CLI-only QA; the runtime reads `ground.json`/`bin`.)*

### ⭐ 2.1 The three tools (target architecture): Survey · Section · Stage

The "Designer = shape" role above is being **separated into two distinct tools**. The full target is **three tools** — each a genuinely different area with its own toolset, each freezing an artifact the next consumes:

| Tool | Authors | Its own tools | Freezes |
|---|---|---|---|
| **Survey** | the **polygon / corner SHAPE** — block silhouette, corner *geometry* (radius), curb. Strokes the centerline chains **outward** into hardscape. | outward stroke, per-corner radius, footprints | the **hardscape shape** — **wall #1, chains die** |
| **Section** | the **ribbons + the internal corners** — treelawn/sidewalk strips, the bent-rectangle corner *fills*, ADA pads, dead-end caps. Strokes **inward** off the frozen curb; LU is the remainder. | inward strokes off the frozen curb | the ped cross-section, authored *onto* Survey's frozen shape |
| **Stage** | the **look / slab** — materials, color, visibility, shaders, sky, post-FX, neon, camera. | (exists today; works on LS) | the **slab** — **wall #2, store dies** |

**The corner is TWO things, in TWO tools.** The corner *shape* (how round the curb silhouette is) is **Survey**. The corner *fill* (how the ped ribbons bend around it — the bent rectangles, the ADA pad) is **Section**. Conflating these two is the root of the corner mess: a fill cannot settle while the shape under it is still moving.

**⭐ Survey and Section are NOT the same — different *data models*, not just different tools.** Survey works in **polygons**; Section works in **ribbons**. The system has deliberate, elaborate machinery to *leave the nodes and chains behind* at the wall and hand Survey clean polygons (faces of the centerline graph) — **separating polygons from ribbons**. *(⚠️ Aspirational for the CURB, 2026-06-09: the tile **topology** is frozen (D2), but the **curb geometry is still re-stroked live from chains** every frame — every NON-Survey view (Section + the neutral Design view) now consumes the frozen `shape.json`; only Survey re-derives live (the idle-case render gate, `BlockGeometryV2Debug` `sectionFrozen = !surveyActive`, 2026-06-16). The curb is the last unfrozen polygon — `PREBAKE.md §4.1`, `SKELETON.md §5f`, `BACKLOG` "Freeze the CURB geometry"; the enforcement checks are in `POLYGON-FIRST.md`.)* So a Survey-stage defect (a block-silhouette dogleg, a corner SHAPE) must be diagnosed and fixed **in polygon terms** — *never* by reasoning back through chains, carriageway centerlines, `pavementHW`, or inner-edge measures, which are ribbon/Section concepts. Sliding from a Survey polygon problem into a chain/ribbon explanation is itself the recurring **bug-class**: it re-couples exactly what the wall exists to decouple. *(2026-06-04: Boz did this diagnosing the park-corner dogleg — explained a polygon step via carriageway `pavementHW` offsets; Jacob's correction: the chains are already gone — work the polygon. The polygon-level question "how should the block silhouette behave at a divided↔undivided transition" is answerable without ever naming a carriageway.)*

**⭐ Troubleshooting heuristic — "wrong in Survey but RIGHT in Section/bake" = the LIVE LOAD PATH, not the geometry (2026-06-16).** Survey and the bake run the *same* `buildTileGround` but on **different inputs**: Section/the bake read the frozen `shape.json`; **Survey live-builds from the store's `centerlineData`**, hydrated by `_loadCenterlines` (`useCartographStore.js`) → `mergeLiveRibbons` → `buildTileGround`. So a defect that shows in Survey but **not** in Section/the bake lives in that live load, **never** in the frozen geometry — check, in order:
> 1. **The measure-resolution chain** `overlay.json > legacy centerlines.json > ribbons.json`. ⚠️ The pre-divided legacy `raw/centerlines.json` carries ONE undivided **by-name** entry per road and **must yield to ribbons for divided carriageways** — else it stamps the whole-road half-width (S-Jefferson 9.16, Lafayette 10.56) onto each carriageway, overrunning the median gap and annihilating the median. This was the **"wrong median on refresh, fixed only by revert-to-skeleton"** bug (fixed 2026-06-16: `isDividedCarriageway` guard in `_loadCenterlines`; `revertSurveyToSkeleton` had bypassed legacy, which is why it "fixed" it temporarily). The node/`buildTileGround`-direct path does NOT apply this resolution, so it can look correct while the browser is wrong — verify in the lit Survey, not a proxy.
> 2. **Persisted overlay edits** (`overlay.json`), and **the render gate** — non-Survey views consume the frozen `shape.json`, so a Survey-exit freeze does **not** change what Survey re-derives on the next load (freezing the shape ≠ fixing the live build).
> 3. **The stale Vite bundle** — `ribbons.json` is a bundled import; a running dev server keeps the old copy until a full restart (`PIPELINE §Wall`).

**Where we actually are (2026-06-02 — vital to hold):** all three tabs **already exist** in the Designer panel — the `ToolPill` in `Panel.jsx` is the 3-part **Survey | Measure | Design** selector (`SurveyorPanel.jsx` / `MeasurePanel.jsx` / default Look editing). **Survey** (`SurveyorPanel.jsx`) already owns: hero-subject pick, the **Smoothing** dial (the Phase-2 stroke-construction silhouette control — live==bake WYSIWYG), street metadata (name/type/oneway), anchor, and **Caps** (round/blunt/none). **Measure** owns the ped widths (treelawn/sidewalk) — it is the future **Section**. So the separation is **consolidation, not from-scratch**: the corner-SHAPE authoring (the on-canvas `CornerEditHandles` radius editor — today it floats outside the panel) + curb width move *into* the existing Survey tab next to smoothing+caps; Measure refits to Section (ped widths + the ribbon corner FILLS + ADA). Section can only be clean once it strokes onto a **frozen** Survey shape — so **corner/ribbon/cap polish in the conflated surface is throwaway** until SHAPE is consolidated into Survey and frozen. (Doc spec: `FEATURES.md` §"The three operator environments" — Survey + Section author the silhouette, the corner editor refines it, the curb traces it; the operator knobs are in `OPERATIONS.md`.)

*(References: the bakes/walls model = memory `project_two_bakes_two_walls`; the outward/inward stroke construction = `project_stroke_construction_model`; the corner invariants that bind whatever builds the shape = `RIBBONS.md §1` — the four invariants.)*

## 3. The Looks model

A **Look** is a styling snapshot. Each Look is `{ design.json, public/baked/<id>/* slab }` plus eventually shader params. The user always works in *some* Look.

Three layers, in order:

1. **Working draft (autosave, always on).** Every panel tweak hits the active Look's `design.json` within ~300ms. Survives reloads. No prompts.
2. **Looks (named saved configurations).** First-class names: `lafayette-square` (the project's 0-state, can't be deleted), `valentines`, `cardinals-win`, `winter`. User explicitly forks via "＋ Save as new Look…". Each carries its own autosaved working state.
3. **Stage channels.** Every Stage channel (materials, color, visibility, sky, post-FX, neon, camera) folds **field-by-field into the Look's `scene.json`** at bake. The once-planned separate `stage-config.json` shader layer never materialized (`DOC-CODE-COHERENCE.md` B1).

**The implicit bake.** Designer's "Stage →" navigates immediately and bakes async in the background, so the Stage view's slab refreshes via `bakeLastMs` cache-bust when the bake finishes. Stage's "↻" re-bakes in place. The user never explicitly "saves the bake" — that language is misleading. The deliberate save action is *forking* into a new named Look.

**Looks are material-keyed, never feature-keyed.** A Look's `design.json` says *"asphalt is pink"*, not *"the asphalt of street id chain-43A12 is pink"*. So adding geometry in Designer never invalidates a Look — new streets inherit the active Look's rules, re-bake just enlarges the slab with consistent styling. **Designer → maintain → Stage is purely additive.**

See `memory/project_cartograph_looks_model.md` for the full decisions.

## 4. Per-helper directory layout

Helpers follow a consistent directory shape so a contributor (or agent) showing up cold can navigate any of them by analogy:

```
<helper>/                  # Build-side: CLIs, server, data sources
  serve.js                 # (optional) Node backend serving the helper's API
  bake-*.js                # CLI: produces the artifact
  data/                    # Inputs the bake reads (geometry, point clouds, etc.)
  README.md                # Contract: inputs, output, endpoints, commands

src/<helper>/              # Runtime-side: React UI for the helper
  *.jsx                    # Editor surfaces, panels, tools
  stores/use*Store.js      # Zustand state for that helper

public/<helper-output>/    # Where the helper's published artifacts live
  …                        # Served as static assets to the runtime
```

Cartograph is the canonical example today. Arborist (scaffolded) is mirroring it; see [`arborist/SPEC.md`](arborist/SPEC.md) for the build plan.

## 5. Runtime composition

The runtime is the public app at `/`. It mounts the rendered neighborhood, loads each helper's artifact, and composes them. The runtime never edits anything — it's read-only over the artifacts.

Key runtime entry points:

- `src/components/Scene.jsx` — main app scene tree
- `src/components/BakedGround.jsx` — consumes a Look's slab (`public/baked/<id>/ground.{json,bin}` + `ground.lightmap.png`), renders as a single fortified mesh with baked AO. Honors `manifest.stencil = null` (toy / scenes without a soft-circle silhouette) by skipping the radial-fade shader.
- `src/cartograph/BlockGeometryV2Debug.jsx` — live-render path for Designer authoring (V2 block-edge-owned ribbons). The retired `src/components/StreetRibbons.jsx` is gone; the shared `src/lib/ribbonsGeometry.js:buildRibbonGeometry()` face-clip helper now has `cartograph/bake-ground.js` as its sole consumer
- `src/lib/buildPathRibbons.js` — shared helper for non-street ribbons (alleys, footways, cycleways, steps, dirt paths). Clipper-based polyline offset with `jtRound` joints and configurable end-cap mode (square / rounded / round). Consumed by both `BlockGeometryV2Debug.jsx` (Designer live render) and `cartograph/bake-ground.js` (slab emission); same input → same geometry, no drift possible.
- `src/components/InstancedTrees.jsx` — consumes the neighborhood's own `public/baked/<scene>/trees.json` + GLB variant atlas. Look resolution: explicit `lookId` prop → `?look=` URL param → `INSTANCE.lookId` (post-Couplers §6). An explicit `bakeUrl` prop wins outright — used where scene ≠ look (toy, Preview/Stage). **No global fallback** (`SLAB-CONTRACT §8`): absent census → no trees, never another hood's.
- `src/components/BakedLamps.jsx` — consumes `public/baked/<look>/lamps.json` and wraps `StreetLights`. Shared between Stage and Preview (was preview-only before 2026-05-13). Same look-resolution pattern as `InstancedTrees`; re-fetches on store `bakeLastMs` change.
- `src/utils/terrainShader.js` — shared terrain-displacement helpers. Every ground-anchored consumer reads from the same `uExag` uniform (driven from `terrainExag.value`, lerped toward `V_EXAG` from `src/lib/terrainCommon.js` by `BakedGround.TerrainExagDriver`). Helpers:
  - `patchTerrain(mat, { perVertex, terrainNormals })` — rigid (sample at `modelMatrix[3].xz`) or per-vertex (sample at each vertex's world XZ). Used by ground, post/rail meshes, foundation paths.
  - `patchTerrainAtCentroidRaw(mat, centroidRaw)` — rigid lift by a precomputed raw value × uExag, via per-material `uCentroidRaw` uniform. Used by building walls where the anchor isn't the mesh origin but the mean-of-footprint-vertices raw (see §8 "Terrain doctrine").
  - `patchTerrainInstanced(mat)` — for InstancedMesh; samples at each instance's world origin and divides the lift by instance Y-scale so the world-space result is `sample × uExag` METERS regardless of per-instance scaling. *(Superseded for lamps/trees by `patchTerrainInstancedBaked` 2026-06-29 — a baked per-object anchor instead of a live sample; see §8 "Ground conformance". Live sampling remains for any future instanced consumer without a baked anchor.)*
  - `BILLBOARD_VS_INC` snippet (in `src/components/StreetLights.jsx`) — lifts billboard quads directly in world space inside the custom ShaderMaterial vertex shader; bypasses three's standard project_vertex chain.
- `src/lib/terrainCommon.js` — `V_EXAG` constant + `makeElevationSampler` (bilinear). Currently `V_EXAG = 1.5`. Single dial for the whole scene; changing it rescales every consumer coherently.

The runtime also re-renders live edits in Designer/Stage during authoring sessions — color changes in Stage Surfaces show on screen *immediately*, not on next bake. The bake then captures a snapshot for handoff.

## 7. Conventions worth knowing

- **Look IDs are slugged user names.** `lafayette-square`, `valentines`, `cardinals-win`. Default Look = `lafayette-square`, can't be deleted.
- **`overlay.json` carries geometry only.** Per-chain `measure` and caps; nothing else. Couplers + segmentMeasures retired with the V2 block-customs migration (2026-05-08); per-block-edge overrides live in `design.blockCustoms` instead. The design block was extracted into per-Look `design.json` files.
- **Materials, layers, land-use** all map through `BAND_TO_LAYER` in `src/cartograph/m3Colors.js`. The bake honors the active Look's `layerVis` to skip hidden materials. As of 2026-05-05, every Designer-Panel toggle has a matching bake group, so what the operator hides in Designer is hidden everywhere downstream (Stage, Preview, production) after the next bake.
- **Leg ribbons and corner pads (historical, pre-V2).** This convention described the chain-rectangle ribbon decomposition that V2 (block-edge-owned ribbons) replaced. The two-pass edge-continuity contract held under that model. Under V2, corners are derived structurally from the same source as legs (rounded-block-clip — see memory `feedback_corner_pad_continuity_first`) and the two-pass framing no longer applies. Retained here as a pointer to the V2 migration rationale; the operational rule today is `feedback_corner_pad_continuity_first`. **Flagged for full rewrite at next cartograph session.**
- **The neighborhood silhouette — one SSOT (`src/cartograph/boundary.js`).** The disc is a **circle, always** (`[[project_neighborhood_disc]]`): center + nominal radius + a 256-pt polygon hugging it, plus two radial feather bands — `fade {inner,outer}` (face-fills) and the wider `streetFade {inner,outer}` (streets trail past faces). All of it loads from **one artifact**, `cartograph/data/<id>/neighborhood_boundary.json` (v2 schema, v1 fallbacks) — *to move or reshape the neighborhood, edit that JSON and re-bake; no code changes anywhere.* `boundary.js` is the **single source of truth every consumer reads** and it does a lot: membership tests `pointInBoundary` / `faceInBoundary` / `streetInBoundary` (bake-time stencil-cull + runtime clip, ~17 call-sites), the radial-fade constants (`FADE_INNER/OUTER`, `STREET_FADE_INNER/OUTER` — face + street shaders), the bake bbox, the raw `boundaryPolygon` outline, and two polyline clippers — `clipPolylineToBoundary` (exact 256-gon) and `clipPolylineToRadius` (cheap exact-circle, used by `MapLayers` to stop debug centerlines at the *visible* feathered edge). The disc is the **Intake-stage** artifact (the protoslab container's geography + boundary; `PIPELINE §intake`, `SKELETON.md §1`). The aerial layer reads the same disc — `AerialTiles.jsx` covers it with a low-res base + an on-demand hi-res **focus** layer (attention-driven, tile-capped, orphaned-fetch-aborting). Banked future payoff: clip-at-bake retires the runtime stencil entirely (wall-move ledger). *(2026-07-03 — this is where the disc gets **written**, by the Extent tool: a fresh scene's boundary is defined by eye and committed to this artifact; see §8 "The Extent tool & the Pour." The pour then uses it as a **data wall** — `pipeline.js` clips derived features to the circle so an overshooting boundary arterial can't skew the content bounds. **⭐ 2026-07-20 — the disc RENDERS, it does not DECIDE.** Membership is `(polygon ∪ activate) − (exclusions ∪ hide)`: the operator's **inclusion polygon** is the test, **exclusion loops** (`nb.exclusions`, persisted alongside) + per-building `activate`/`hide` are corrections, and the disc is only the **fallback** when a scene carries no polygon — `NEIGHBORHOOD-INPUTS §5.2`. ⛔ *This parenthetical previously stated the 2026-07-14 **excluder model** — "the disc … IS the membership boundary, every building inside is IN" — which was RETRACTED; it made subtraction the only gesture and silently cost 147 Księży Młyn buildings. Fixed in the 2026-07-23 canon sweep.*)*
- **Coordinate systems.** World-meters with origin at the neighborhood center, in **compass frame** — equirectangular GPS→meters projection, no rotation applied. One frame, every dataset. The earlier "de-parking" episode (May 2026) briefly introduced a parallel park-aligned world frame at -9.2°; that duality was misdiagnosed and reverted. The screen-orientation desire is camera-only, lives on `SHOTS.browse.up` (the Heading slider). The park grid's real ~9.2° rotation from compass-N is *real-world geometry baked into the coords*, not a coordinate choice. **The firebreak:** the only legitimate uses of a 9.2°-related constant are `LafayettePark.parkAxisToCompass` (a fence-corner authoring shortcut) and the Browse `up` vector (cosmetic); any *other* `9.2` / `-9.2` / `0.1605`(rad) / `Math.PI/19.57` / `GRID_ROTATION`-shaped constant in the math/data layer (bake scripts, store actions, geometry builders, shaders) is vestigial from the de-parking episode and should be **removed, not preserved** — this number has cost many hours. History: `project_compass_only_camera_heading`.
- **Visible geometry is permanent; derivation can change.** A geometric region defined by the world model — the rounded asphalt mouth at every IX, the wedge between a rounded curb arc and the straight ped-band edges that meet at a block's corner, the half-disc at a cul-de-sac — must always be filled in V2's output, regardless of which emitter computes it. What changes when an emitter is rewritten (e.g., chain-rectangle decomposition → block-edge ownership) is *how* a region is derived, not whether it exists. Designer + bake + Preview + Stage all consume the same V2 output, so any visible regression in Designer cascades to Preview. The honest test for "is this code cruft" is **not** "does the new architecture's mental model exclude it" but "does the visual region this code fills still need to be filled." If yes, keep it; if a future emitter produces the same region cleaner, *replace* the derivation, don't delete and hope. The concrete corner pad (`buildCornerPadQuad` / `cornerSidewalkPads`) and asphalt corner plug (`cornerAsphaltPlugs`) in `src/lib/buildBlockGeometryV2.js` are the canonical examples — see the ⚠ guards there and the `feedback_load_bearing_corner_pads` / `feedback_no_speculative_cruft_lists` memory entries. Distinct from this: pure derivation patches (per-chain rectangles' winding-cancellation gaps, race-condition workarounds, debounce shims) are tied to the emitter and DO go away when emitter assumptions change.
- **Scenes route through one pipeline.** A scene (toy, lafayette-square, future neighborhoods) is a different *dataset*, not a different code path. Same server endpoints (scene-parametric), same store loaders, same render components, same Survey/Measure tools. If you find yourself writing `if (scene === 'X')` branches, parallel emitters, or hybrid mounts, the architecture is wrong; revert and make the canonical pipeline scene-parametric instead. See `cartograph/TOY_AUTHORING_PLAN.md` (Phase 0) for the per-scene file layout (`src/data/<scene>/centerlines.json` + `overlay.json`) and the scene-parametric route shape (`/api/cartograph/:scene/...`). Memory entry: `feedback_no_parallel_pipeline_for_scenes`.
- **All Canvas mounts opt into `logarithmicDepthBuffer: true`.** Both Cartograph Stage and Preview pass this on the Canvas's `gl` prop. Reason: the scene spans ~2km horizontally with sub-meter Y separations (water 0.35m above ground, paths 0.4m). With linear 24-bit depth + near=1/far=60000, 90%+ of precision lives in the first few meters and high-altitude Browse renders sub-meter Y gaps as unresolvable — water sorts into ground, treelawn snaps off, etc. Logarithmic redistribution makes sub-meter separations robust at any reasonable distance. See **§8 "Layering / coplanar stacking / depth precision"** for the full canon of which-mechanism-when. Any future Canvas in the project should match. **Corollary (2026-05-18):** `polygonOffset` is structurally inert under this Canvas — the `<logdepthbuf_fragment>` chunk writes `gl_FragDepth` explicitly, which per the GL spec bypasses `GL_POLYGON_OFFSET_FILL`. Coplanar resolution among transparent meshes uses `renderOrder` ordering; among opaque, Y separation. Raw `ShaderMaterial`s must additionally include the four `<logdepthbuf_*>` chunks manually (built-in materials chain them automatically). Memories: `feedback_raw_shadermaterial_needs_logdepth_chunks`, `feedback_polygonoffset_inert_under_logdepth`.
- **Stage / production gating via prop presence (2026-05-18).** Components that gate behavior differently between Stage authoring (where a panel toggle should be a master switch) and shipped production (where authored data — hours, schedule, etc. — should be the sole arbiter) take the toggle as an *optional prop*. Prop passed = Stage path, toggle is master. Prop omitted = production path, authored data is the sole gate. The canonical case is `<LafayetteScene forceNeonOn={…}>` (Stage, neon visibility) vs. `<LafayetteScene>` (production, neon visibility gated only by `_isWithinHours`). The pattern beats OR-chains of independent gates (which produce additive-override confusion and break the panel-toggle-as-master expectation). Memory: `feedback_panel_is_source_of_truth_for_authored_channels`.
- **Night darkness lives in the sky layer, not in scattered floors — the "Sky Layer Gain" channel (2026-06-07).** Deep-night sky read too bright because "night brightness" was the emergent sum of ~4 independent hardwired floors (linear sky bands lifted by ACES+sRGB; a bloom night `dk` boost; the `<ambientLight 0.45>` ground floor; an additive horizon glow) — turning any one down left the others holding the floor up. The cure: ONE owner. `skyGain` (Light & Sky card, panel label "Sky brightness" since 2026-06-30) is a single gain applied **last** in the GradientSky fragment shader (`finalColor *= uSkyGain`), scaling the entire composed dome (bands + sun/moon glow + horizon scatter + haze). It is **exposure scoped to the sky layer**, the key distinction from global `exposure`: `exposure` dims the whole frame (buildings + ground + sky); `skyGain` dims *only* the dome, so deep night goes dark while lamps + lit windows stay where authored. Generalizes the planetarium `dimFactor` already in `CelestialBodies`. **Stars are a separate object (own `astronomyAlpha`) and are deliberately NOT scaled** — dimming the dome makes them read better. Default `1.0` = no-op (unauthored Looks unchanged); the canonical use is a TOD curve holding `1.0` by day and dipping to ~`0.2` at Night. **Paired hardwire removal:** the bloom night `dk` boost was deleted from both `PostProcessing.jsx` and `PreviewPostFx.jsx` (it overrode the authored bloom channel and, with a low authored threshold, drove the luminance threshold negative → whole-frame bloom). Bloom is now operator-authored only; lamp glow (independent geometry in `StreetLights.jsx`, not bloom) carries night legibility. This is "hardwires-come-out" applied to the night look — and night now drops its single most expensive post pass. Wired the standard channel way (`skyLightChannels.js` → store → `CartographSkyLight` slider → `CelestialBodies` consumer → `CartographApp` override → `bake-scene` → `scene.json`). See `NOTES.md` 2026-06-07.
- **Post-FX shares a blur LADDER, not a single blur — DoF + bloom each take their character off it (2026-06-26/27).** `DownsamplePyramid.jsx` exposes its **mip rungs** (8 levels, tight→wide) via `_pyramidRefs.levels` — the one expensive downsample, sampled many ways (gang intact → phone budget). **DoF** (`RomanceDoF.jsx`) picks blur **radius** by depth (2-tap lerp of the straddling rungs) → a real focus pull; *single-focal* (sharp near → mid/far melts), which **replaced the two-focal model** (it read backwards — pushing Focus out blurred the *near*, since everything closer than the far plane was "foreground"). A **hero pocket** eases the far blur toward `heroBlur` at the designated hero's distance (the gentle-soft Arch). **Bloom** (`CustomBloom.jsx`) is a **band-pass**: glow on bright *contrast* (`rung_i − rung_{i+1}`), so lamps/edges glow and a bright sky **backlights** dark objects as a rim, while uniform areas (open sky, the Arch's body) don't wash. Bugs worth banking: (1) **anchor the hero pocket in VIEW-Z space** — the shader decodes depth as forward-axis Z, so `camera.distanceTo` (Euclidean) missed the off-axis Arch; (2) feed the **live** hero placement via override, not the stale baked `scene.json` arch; (3) bloom is **ADDITIVE** (SCREEN *darkens* HDR-bright pixels: `screen(2.0,g) < 2.0` → washed the sky); (4) DoF's browse-disable gates on the camera looking **down**, not raw height (the height gate killed DoF in the elevated Hero shot). Debug: `window.__dofDebug = 1` paints the focus zones. Landed `7d1bb238` + follow-ups; arc detail archived `_archive/HANDOFF-real-dof-2026-06-27.md`.
- **Two legibility levers for "moody-but-readable" looks — sky-coloured fill + an additive lift (2026-06-30).** Authoring the overhead **Browse** look exposed that the map read black not for lack of brightness but for lack of the *right* levers: the fill was flat white, and `exposure` is a *multiplicative* gain (near-0 albedo × any factor ≈ 0 — it can't lift crushed blacks). Two fixes, both kit-level (`scratch/LOOK-PANEL-TAXONOMY.md`): **(1) the hemisphere fill (`hemi`, "Sky fill") is now driven by the live sky gradient** — `<hemisphereLight>` `color = lighting.sky.top` (up-sky) and `groundColor = lighting.sky.bottom` (warm horizon bounce), with `hemiBase` raised `0.35→0.55` so it's a real lever (`CelestialBodies.jsx`). It washes up-facing surfaces in the *sky's own colour* — the "surfaces glow with the sky" result — where flat `ambient` only adds colourless fill. **(2) a `brightness` field on the `grade` channel** — an *additive LIFT* `c = c + uBrightness·(1−c)` in `FilmGradeEffect` (`PostProcessing.jsx`) that raises the black floor while leaving the white point put (the "B" of HSB; Saturation = the "S"). This is the lift `exposure`'s multiply structurally can't do; it un-crushes dark ground while highlights hold. The dead **Grade›Toe** field was removed in the same pass (the `fill`/"Shadow lift" channel owns the FilmGrade `uToe`, so Grade's Toe slider did nothing).
- **Shared clock + calendar anchor.** `src/hooks/useTimeOfDay` (current minute-of-day) and `src/hooks/useCalendar` (current date, day-of-year, season) are kit-level singletons. ANY helper that needs time or season consumes these — never mints its own. Each helper hosts its own scrub UI (DawnTimeline for TOD, DateScrubber for date) over the shared state. `<ClockCalendarPump mode="live">` mounted in a production scene ticks both from wall time; authoring tabs leave the pump off and let scrub UIs drive. Drift-prevention rationale in `meteorologist/NOTES.md` 2026-05-20 ADR.
- **Grade separation is a frame fact, carried per street; junctions never hold it (Groma 2026-06-02).** OSM `layer`/`bridge`/`tunnel` mark elevated/buried roadway. The frame (`skeleton.js#gradeFields`) summarizes them over *all* of a welded chain's `chain.sources` and emits per street: raw `layer`/`bridge`/`tunnel` + an operative `gradeSeparated = entirelyOffGrade || isLimitedAccess(highway)`. These survive `derive.js`'s serializer whitelist into `ribbons.streets`. **Why:** the visible degenerate polygons (interchange triangles, slivers, false blocks) are grade-separated centerlines that cross in 2D **without a shared vertex** — the planar face walk (`tileGround.extractFaces`, shared-vertex-only graph) has no node there, so the crossing edge bowties the faces. The fix is the consumer excluding `gradeSeparated` streets from the face graph (`streets.filter(s => !s.gradeSeparated)`), **not** patching faces downstream (§Wall). **Invariant:** `skeleton.junctions` is shared-vertex-only, so grade-separated crossings (which share no vertex) are **never** false-typed as junctions — don't hunt grade bugs in `junctions[]`. **Tag-free truth:** OSM has 0 same-layer crossings lacking a shared node, so any no-shared-vertex 2D crossing *is* a grade separation. Decision: `gradeSeparated` folds in limited-access class (motorway/trunk + links) because those corridors abut frontage roads and never bound neighborhood blocks; partly-bridge *surface* streets (Mississippi, Nebraska) stay `gradeSeparated:false` and keep bounding blocks. *(This section is the live home for grade-separation doctrine; the originating `HANDOFF-onframe-faces.md` is retired.)*
- **Per-shot look overrides resolve at ONE point per surface, so consumers stay shot-blind (the channel-variant cascade, 2026-06-29).** A Look authors a base look (Hero); a `browse`/`street` shot can override any LOOK channel sparsely (`shotLooks[shot][channel]`), inheriting base elsewhere. The merge — `effectiveScene = {...base, ...shotLooks[shot]}` — is folded into the SINGLE shared read each surface already uses, NOT pushed per-consumer: **production** resolves off the camera `viewMode` inside `useSceneJson` (`src/lib/shotScene.js`) so every render consumer reads `scene.<channel>` unchanged; the **Stage** resolves off the active `shot` via `activeChannel(s,name)` in `useCartographStore` (every panel-edit + render-override read + the LampGlow/Neon pumps route through it). This is the blast-radius win — the alternative (a per-consumer `resolveChannel(shot)`) would have touched ~25 render sites. **Caveat / firming gap:** `SlabBuildings` fetches `scene.json` *directly* (its own `fetch`, bypassing `useSceneJson`), so building material (`materialColors`/`materialPhysics`/`palette`) can't fork per shot until that read is routed through the adapter — building material stays global by design today. Sparse + opt-in: an unforked Look omits `shotLooks` and is byte-identical. See `STAGE.md §1.5`, `SLAB-CONTRACT.md §4`, `HANDOFF-channel-variant-cascade.md`.
- **Bake writes go through `cartograph/io.js`'s `writeIfChanged`.** Two contracts: skip the disk write when bytes are byte-identical (cheap), AND touch the output's mtime to "now" on every successful call. The second contract is canonical-`make` behavior — without it, editing a source script (`pipeline.js`, `bake-ground.js`, etc.) permanently invalidates its downstream artifact, because the no-op write never bumps mtime and `needsRebuild` reruns every step on every bake. Any new bake step must use `writeIfChanged` for its outputs. If the step ALSO patches another step's output (e.g., AO patches the ground manifest), patch first, output last — otherwise the patch ends up strictly newer than the step's own output and `needsRebuild` reruns the step every bake. See **§8 "Bake chain"** for async + cache-bust + the verified 1ms no-op behavior. **⚠️ Exception — input artifacts (`{touch:false}`):** the mtime-bump (contract 2) is for *outputs* inside the dirty graph. An artifact that is only a needsRebuild **input**, produced *outside* serve's graph by a manual run (e.g. `skeleton.json` from `node skeleton.js`), must pass `writeIfChanged(…, {touch:false})` — otherwise every no-op run bumps its mtime, looks like new input, and forces a full downstream rebuild (the `skeleton.js` drift gremlin; `e3ec84a`, ledger C10).

## 8. Render & bake internals (the load-bearing decisions)

> The canonical home for the render/bake engineering decisions — migrated out of FEATURES (2026-06-14) so FEATURES stays the pure pitch. Operator-facing knobs are in `OPERATIONS.md`; the plain-language doctrine is in `/ORIENTATION.md`. (§7 above already carries several of these as conventions — sky-gain, grade-sep, the logdepth corollary, gating, `writeIfChanged`; this section holds the ones that needed a full home.)

### Layering / coplanar stacking / depth precision
Four mechanisms keep coplanar surfaces from fighting; picking the wrong one is the most common "the X is missing in Stage / the Y looks weird at distance" bug.

| Mechanism | Handles | Works | Failure mode |
|---|---|---|---|
| **Geometric Y separation** (water 0.35m above ground, paths 0.4m, trees on top) | surfaces genuinely at different heights | all distances (with log-depth on) | visible gap if too aggressive |
| **`polygonOffset` per renderOrder** (`polygonOffsetUnits: -renderOrder`) | coplanar surfaces at y=0 (face fill + bands + stripes) | within reason | precision-relative; **structurally INERT under this Canvas — see below** |
| **Tiny Y-lift (0.01m)** (`block 0.01 → asphalt 0.04 → paths 0.05`) | **Designer ortho view only** | top-down ortho | fragile; never for Stage/Preview |
| **`renderOrder` + transparent** | transparent overlays with known monotonic order | forces draw order | wrong if surfaces aren't genuinely in front |

**The fifth axis — depth precision at distance.** All Canvas mounts set `logarithmicDepthBuffer: true`. Without it, linear 24-bit depth over `near=1, far=60000` puts 90%+ of precision in the first few meters, so at Browse altitude (1300m+) the 35cm water-above-ground gap sorts into the ground. Log-depth redistributes precision so sub-meter gaps resolve at any distance (~5% perf, acceptable on mobile). **Corollary — `polygonOffset` is structurally inert here:** the `<logdepthbuf_fragment>` chunk writes `gl_FragDepth` explicitly, which per the GL spec bypasses `GL_POLYGON_OFFSET_FILL`. So: resolve coplanar **transparent** meshes with `renderOrder`; **opaque** with Y separation. Raw `THREE.ShaderMaterial`s must manually include the four `<logdepthbuf_*>` chunks + `defines:{USE_LOGDEPTHBUF:''}` (built-ins chain them automatically) or they write linear depth and disappear at some camera angles. *(Memories: `feedback_raw_shadermaterial_needs_logdepth_chunks`, `feedback_polygonoffset_inert_under_logdepth`.)*

**Decision rule for a new ground layer:** real physical height difference → Geometric Y (≥1cm) · coplanar overlay → `polygonOffset` per its renderOrder slot · Designer-only authoring overlay → tiny Y-lift OR transparent+renderOrder · "always on top" overlay → `renderOrder` + `depthTest:false`. Custom shaders need a unique `customProgramCacheKey` before any `patchTerrain` wrapper, or three's program cache silently collapses them onto another material's compiled shader. Per-pond rigid lift (`<PondGroup>`), not per-park and not per-vertex, for stacked bank/water/island.

### Ground conformance — one DRAWN surface, everything sits on it (2026-06-29)
"Nothing sits on the ground" had two roots, both now cured; together they are the **conformance doctrine** that supersedes the bare "coverage parity" rule below.

- **One field — CPU↔GPU reconcile.** There is one heightfield (`terrain.bin`) but two samplers, and they used to index it at *different positions*: the CPU bilinear (`terrainCommon.makeElevationSampler`) reads grid index `u·(N−1)`; a raw `texture2D` reads texel centers `u·N−0.5` — up to **±0.5 cell (±2.5 m horizontal, ~2 m vertical at the steep edges)** apart, zero only at the domain center. A CPU-placed object on a GPU-rendered ground therefore floated. **Cure:** the GPU snippets remap their coordinate through `_terrainUV` (`terrainShader.js`) so `texture2D` lands on the CPU grid index — the two paths now return **byte-identical** world-Y. Reconcile direction is GPU→CPU on purpose: buildings/foundations anchor on the CPU convention (below), so the ground comes to *them* and they never move.
- **One DRAWN surface — baked object anchors.** The rendered ground is a *coarse triangle mesh*; objects that point-sample the *smooth* field only agree with it at vertices, floating up to the face tolerance (0.5 m) between them — worse on the unrefined ribbon ground. Refining the whole ground to close this is a perf dead-end (tol 0.25 → 2× the ground tris, undoing the mobile tri-cut). So instead of bringing the ground to the objects, bring the **objects to the drawn ground**: `cartograph/groundSampler.js` (`groundRawAt(x,z)`) samples the *baked ground mesh* (barycentric over the top-most group's triangle) and a per-object **baked anchor** rigid-lifts by `groundRaw × uExag` via **`patchTerrainInstancedBaked`** — exactly the buildings/foundations `aCentroidY` regime, generalized to point objects. Perf-free (no added ground tris), exact at every exaggeration. This is the **shared-resource / pyramid pattern**: one canonical ground surface, every element redistributed onto it — not each object re-deriving terrain.
  - **Lamps** bake `groundRaw` into `baked/<look>/lamps.json` (`bake-lamps.js`); post + glow + bulb all rigid-lift, so they stay locked together on the lantern.
  - **Trees** carry a per-look anchor in `baked/<look>/tree-anchors.json` (`bake-tree-anchors.js`), **index-parallel to that look's own `trees.json`** — which is why the anchor bake MUST read the same placements file the runtime reads; the runtime discards the whole array on a length mismatch and the trees fall back to floating on the smooth field. `InstancedTrees` injects `groundRaw` per instance (mesh + impostor), material → `patchTerrainInstancedBaked`. (Removed up to 0.53 m of lamp float / 1.9 m of tree float.) *(Corrected 2026-07-15: trees were described here as "global (`baked/default.json`)" and the anchor bake hardcoded that path, so it could only ever anchor LS. Placements are per-neighborhood — `SLAB-CONTRACT §8`.)*
  - **`patchTerrainInstanced` (live field sample) is superseded for lamps/trees** by `patchTerrainInstancedBaked` — update the coverage-parity line below accordingly.
- **Where the surface itself must be faithful** — park gravel paths ride the rolling park, so `park_path` gets a dense uniform contour refine (`CONTOUR_REFINE_KEYS`, `PATH_CONTOUR_REFINE_MAX_EDGE_M = 6`) instead of skipping refinement like other ribbons; the object-anchor approach handles point objects, refinement handles the path *surface*.
- **Bake-chain order (load-bearing):** `bake-lamps` + `bake-tree-anchors` read the look's ground mesh, so they MUST run **after** `bake-ground` (and trees after the global tree bake). ⚠️ verify `serve.js` enforces this before relying on auto-bake.
- **Trunk-base colour** rides the SAME drawn-ground idea on the colour axis: the trunk's lowest ~1.5 m blends toward the **combined effective** ground colour — albedo (`ground.colormap.png`) × baked contact-shadow + lamp pool (`ground.poolmap.png`), the same math `grassMaterial` uses — so the trunk sits *in* its own shadow ring, not as bright raw albedo. Wired in `treeAtlasMaterial.js` (shared `groundColorState` FX map), 2026-06-29.
- **Surface treatment — desaturate + value-lift (2026-06-30, ⚠️ prototype).** The authored `layerColors` palette runs value ~40–178 with saturated lots, so under dim TOD light the dark layers (ground 40, asphalt 74) crush to black while sidewalk (178) blows white — and saturated albedo fights the "lit by the sky's colour" goal. `BakedGround.jsx` `FadeMesh` now runs `treatAlbedo()` on the baked `group.color`: pull chroma toward gray + compress lightness UP off black (HSL, `SRGBColorSpace`), so every layer reads as a gentle value step that the sky-coloured fill then colours. ⚠️ **Currently three hardcoded constants (`SAT 0.30 / FLOOR 0.22 / CEIL 0.72`), flagged to become a "Surface" look KNOB** (per `feedback-no-hardcoded-ramps-use-knobs`) — applies to `FadeMesh` only so far (grass/gravel shaders still carry their own chroma). `scratch/LOOK-PANEL-TAXONOMY.md` Phase B.

### Terrain doctrine — one dial, corner-mean anchor
Every ground-anchored consumer multiplies by the same `uExag` uniform (driven from `terrainExag.value`, lerped toward `V_EXAG` in `terrainCommon.js`; currently `1.5`). **`V_EXAG` is the single dial** — changing it rescales the whole scene coherently (ground, foundations, buildings, lamps, trees, paths, water). **Anchor rule:** the rigid-lift "centroid Y" is the **mean of `getElevationRaw` at every footprint vertex**, never a single sample at `building.position` (sampling at position diverges by the heightfield's convexity — ~0.5m of baked-in over-exposure on LS's concave hill). Both building walls (`patchTerrainAtCentroidRaw`) and foundations (per-vertex `aCentroidY`) use it. **Instance-scale:** `patchTerrainInstanced` divides the lift by instance Y-scale so the world result is `sample × uExag` meters regardless of scale (else lamps/trees over-lift). **Coverage parity:** anything ground-anchored must patch (`patchTerrain` perVertex for ground; `patchTerrainAtCentroidRaw` for walls; `aCentroidY` for foundations; **`patchTerrainInstancedBaked` for lamps/trees** — baked per-object anchor, see "Ground conformance" above, which superseded the old live `patchTerrainInstanced`; `BILLBOARD_VS_INC` for billboards) — and disable frustum culling on GPU-displaced meshes (the CPU bounding sphere is computed from un-displaced Y=0 positions, so the mesh culls while still on-screen — "buildings pop out as I pan"). **Triangulation density:** `bake-ground.js`'s `triangulateAndRefine(outer,holes,refine)` subdivides face/landscape polygons so per-vertex terrain sampling doesn't linearly-interpolate across a curving heightfield (the "foundations too tall / paths in midair on flat blocks" artifact; ribbons skip — their authored density already matches). Two properties to know: **(1) adaptive** — the default (`GROUND_REFINE="adaptive"`, `OPERATIONS.md §Ground tri-budget`) splits a triangle only where the heightfield bends past `GROUND_REFINE_TOL_M` (0.50 m), not on a uniform `maxEdge` grid — the tri-budget lever (1.37M→~0.5M tris). **(2) conforming (red-green)** — the split is crack-free: a criterion-selected triangle goes 1-to-4 (red); any neighbour whose shared edge it bisected conforms via a 1-to-2 green closure, or is promoted to red if ≥2 of its edges are bisected (iterated to a fixpoint). ⚠️ **A per-triangle split *without* this conformity leaves T-junctions** at every adaptive refined/coarse boundary — up-to-`tol` vertical cracks along the contours, invisible overhead but glaring at street level (the bug that shipped 2026-06-17, fixed same day). Per-polygon triangulation is independent, so the conforming guarantee is *within* a polygon; cross-polygon (group-boundary) conformity is not yet handled. ⚠️ **A ground geometry re-bake rewrites `ground.json` without the AO `lightmap` block — always re-bake AO after** (`BACKLOG.md` GPU-perf thread).

### Building x-ray — camera see-through (always on, 2026-06-28)
`SlabBuildings` dissolves any building the camera is *inside* so you never see the hollow cross-section the near-clip would slice — the camera gets a clear shot through. A fragment within `uDissolveDist` (12 m) of the camera position fully discards; a dither band `uDissolveBand` (9 m) above it softens the edge (a hashed `gl_FragCoord` `discard`, so it needs no transparency sort). The gate is camera **distance** (`distance(vBPos, uCamPos)`), **not height** — so roofs passing far below on a fly-over stay solid; only walls the camera interpenetrates fade. `uCamPos` is fed per-frame in the `SlabBuildings` `useFrame`; `uDissolveDist`/`uDissolveBand` are module consts, live-tunable via `window.__bldgXray(dist, band)`. **Decision — automatic, not a knob:** this is artifact suppression (same family as frustum culling), not a look channel — there's no value in ever *seeing* the broken cross-section, so by the no-hidden-look-math rule it is **not** a knob (a knob is for authored look variation; `feedback-no-hardcoded-ramps-use-knobs`). The earlier gated toggle (`useCamera.buildingDissolve` + a BrowseHeader button, 2026-06-25) was removed when it went auto. If the dither band ever flickers on a specific path, promote DIST/BAND to a real authored knob *then* — don't pay for the escape hatch up front.

### Neon renderer
One merged shader mesh per scene (`NeonBands.jsx`), mounted in `LafayetteScene` (Stage + production) and `ToyBuildings` (toy). Full-circle cross-section (`CROSS_SEGS=8`), tube center at the rooftop seam, `TUBE_RADIUS=1.0m` (0.3m was sub-pixel past street level). Winding: outward direction via point-in-polygon probe of the first-edge midpoint (robust to LS's mixed CW/CCW). Material: `DoubleSide` + `AdditiveBlending`, raw `ShaderMaterial`, **no `gl_FrontFacing` flip** — back faces clamp to a dim bleed glow → the omnidirectional emissive look (don't "fix" this; `feedback_neon_cylinder_doubleside_no_flip`). **Geometry is never baked** — tubes runtime-build everywhere; the bake carries only intensity uniforms (`scene.json.neon.values`). `tubeRadius` is the one geometry-driving channel (rebuilds on change, step-quantized). Gate split: `forceNeonOn` present = Stage (panel toggle is master); omitted = production (hours gate is sole arbiter) — see §7 gating convention.

**Two-stage gate — WHICH tubes (open-by-hours) × HOW bright (TOD intensity). Both must work or neon is dark:**
1. **Which tubes light** (`SceneNeon.openPlaces`): a building's tube is included iff its listing's authored `hours` intersect the current `useTimeOfDay.currentTime` (`_isWithinHours`; live ≈ real now). Listings carry `hours` as a parsed **object** (`{monday:{open,close}}`); the Apps Script backend parses `hours_json`→`hours` server-side (`Code.js`), and `useInit`/`useListings` ingest objects. Bare buildings (no hours) stay dark. `CATEGORY_HEX[category]` must resolve or the listing is skipped.
2. **How bright the tubes are** (the `_neonUniforms` core/tube/bleed/emissive): the neon channel is `animated:"tod"`, so `scene.neon.values` is **slot-keyed** (`{golden:{…}}`). It MUST be resolved per the current TOD slot (`resolveGroupAtMinute(scene.neon, minute, slotMinutes, NEON_FIELD_KEYS, NEON_FLAT_DEFAULTS)`) — **two drivers**: Stage = `CartographApp.NeonPump` (per-frame, live store); production/Preview = `NeonBands` mount-time effect (`scene.json` baseline). ⚠️ **Regression cured 2026-06-29:** production's effect *flat-read* `scene.neon.values.core` — `undefined` for an animated channel → core/tube = 0 → tubes built but rendered at zero intensity → **invisible** (force-on "worked" only because Stage's NeonPump resolves). Both drivers now resolve. (The open-by-hours gate was fine throughout — diagnosed by instrumenting `openPlaces`; lesson `feedback_worked_before_means_regression`.) *(`hours_json`→`hours` parse was added to `useListings` as defensive normalization but is a no-op against the current backend, which already parses it — NOT the fix.)*

### Time-of-day channels & sky dome (2026-06-28)
- **TOD channel resolver semantics.** A TOD channel with a SINGLE keyframe resolves to that value at ALL minutes (`resolveAnimatedAtMinute` / `resolveGroupAtMinute`, `src/cartograph/animatedParam.js`). Consequence: flipping a flat channel to `animated:'tod'` with only one slot **globally overwrites the rest of the day** — so a flat→animated conversion MUST seed an anchor slot (noon/night) with the prior flat value. Channels promoted to TOD this way: lantern, ambient, exposure, halo, mist, dof, warmth, dirMoon, fill.
- **DoF is a TOD channel; its mount gate is animated-aware.** `PostProcessing.jsx` mounts `RomanceDoF` when dof is enabled. A TOD-animated dof nests `enabled` per slot, so the gate mounts if ANY slot enables it (fixed 2026-06-28, `4ca9ab5f` — it previously read only flat `dof.values.enabled` and never mounted an animated dof). The per-frame `dofDriver` resolves blur per-minute; sharp slots are a near-noop. DoF blur is force-zeroed in the Browse (look-down) shot.
- **EffectComposer key + HMR.** The composer key is `fx-${smaaOn}-${dofOn}`; flipping dofOn/smaaOn rebuilds it. Under Vite HMR a rebuild can leave a consumer's driver detached (presents as "bloom went dark"), cured by a hard reload — NOT a real DoF↔Bloom coupling. DoF + Bloom share the `DownsamplePyramid` BY DESIGN; do not un-share (see §7 post-FX ladder + the bloom-foliage-freeze shared-pyramid history).
- **Sky dome = seasonal hour×band grid + sparse overrides.** `skyGrid.js`: a per-season anchor-card grid (24 hours × 5 bands: horizon/low/mid/high/sunGlow), resolved per date+minute. Per-Look colour authoring is `scene.json` `sky.overrides` — a sparse list of `{hour, band, hex}` cells, each feathered spatially + temporally. ⚠️ **Overrides are keyed by CLOCK HOUR** (and apply across all seasons at that hour), **NOT by TOD slot** — so slot-relative colour (sunset/dusk) doesn't track across seasons. Known limitation; the Sky Builder is the season-aware authoring tool.

### Render pipeline — one manifest, installed everywhere (2026-06-30)

The post-FX stack is **declared once and installed identically in production, Stage, and Preview** — parity by construction, not by assertion. (Landed Phases 1–3 of `HANDOFF-render-pipeline-install.md`; commits `cba425b1`/`99098910`/Phase-3.)

- **The manifest** (`renderPipeline.jsx` → `POSTFX_PIPELINE`) is the machine SSoT of *what ships*: an ordered list, each entry `{id, pass, channel, order, platform, gate, props}`. It is the literal ship list — reading it tells you the whole post-FX stack.

  | order | id | pass | channel | platform |
  |---|---|---|---|---|
  | 10 | ao | N8AO | ao | desktop |
  | 20 | pyramid | DownsamplePyramid | (shared resource) | desktop |
  | 30 | dof | RomanceDoF | dof | desktop |
  | 40 | bloom | CustomBloom | bloom | (all) |
  | 50 | aerial | AerialPerspective | halo | desktop |
  | 60 | grade | FilmGrade | grade | (all) |
  | 70 | smaa | SMAA | smaa | (all) |
  | 80 | grain | FilmGrain | grain | (all) |

- **The installer** (`RenderPipeline`) consumes the manifest, filters by `platform` + `gate`, and mounts passes in order with the correct remount key. `PostProcessing.jsx` is now a **thin mode wrapper**: resolve channels → `usePostFxDriver` (the ONE per-frame driver — channel resolution, all module refs, DoF absorbed) → mount `<RenderPipeline>`.
- **Mobile is a `platform` field, not a code fork.** The old `if (IS_MOBILE) return <minimal composer>` collapsed into the manifest (mobile currently *drops* ao/pyramid/dof/bloom/aerial). ⚠️ **Still stripped on mobile** — but now flipping "drop" → "low bracket" is a one-field edit, not a fork (the mobile-viability lever; gated on `preview-measurement`'s real device numbers).
- **Inspection is a parameter, not a parallel composer.** Preview mounts the *same* installer with `inspect={ toggles, onCost }`; the toggle gates each pass + joins the remount key. **`PreviewPostFx` is retired** (the fork that silently drifted — its DoF driver was URL-param-based + missing heroDist/gates → Preview's DoF was wrong; folding onto the installer *corrected* it). "Preview == Production" is now structural.
- **Decision (why):** a fork duplicates the pipeline + the driver and drifts (proven — Preview's DoF rotted). Declaring the pipeline once + installing it by mode makes "add a pass / fix a driver / change an order" touch *one* place, inherited by all three surfaces. The `platform` field also **absorbs `preview-measurement`'s inclusion manifest** (one SSoT, not two). Follow-on Phases 4 (the scene tree onto the same manifest) + 5 (fold render-conformance/preview-measurement in) remain in the HANDOFF.

### Bake chain — async, cache-bust, dirty-skip
- **Async handler:** `serve.js` POST `/looks/:id/bake` runs each step via `runShell` (non-blocking); a per-look `_bakesInFlight` set rejects concurrent bakes against the same Look (409) so a double-click can't race two writers.
- **Cache-bust:** `BakedGround`/`InstancedTrees` fetch `?t=${bakeLastMs}`; **`bakeLastMs` must be `Date.now()` on every bake completion**, never the bake duration (reusing a duration value lets the browser serve stale geometry — "I edited days ago, Stage doesn't show it").
- **Dirty-skip:** `writeIfChanged` (§7) — skip identical bytes, but touch mtime on no-op; **patch another step's output before writing your own** (else the patch is newer than your output and `needsRebuild` reruns you every bake). Input artifacts produced outside serve's graph (e.g. `skeleton.json`) pass `{touch:false}`.

### The Extent tool & the Pour — the no-CLI intake→3D arc (2026-07-03; procedure rewritten 2026-07-20; D4 + identity lock + the palimpsest warning added 2026-07-23)
The whole intake→3D arc (define a new neighborhood → derive → bake → land in Designer) is **one tool, no terminal.**

> ⭐ **Design of record: [`/EXTENT-DESIGN.md`](../EXTENT-DESIGN.md)** (ratified 2026-07-22) — what the tool *makes* (the **served skeleton**, which is a **labeled point cloud** + node stamps, not the boundary disc), the **hood < disc < bb** size model, the two centers, the **seal as the identity registry**, and the ordered v1 worklist. `/EXTENT-EXCAVATION.md` is its evidence layer; `INTAKE.md §0.5` is the as-built operator flow; `OPERATIONS.md §Extent` is the manual. **This section is the as-built engineering record** — read EXTENT-DESIGN before changing the model.

**⭐ THE PROCEDURE, as-built.** Three boundaries, three jobs — they are routinely conflated and the field names actively mislead (`boundary` is the 256-gon RENDER disc; `polygon` is MEMBERSHIP):

| | job | reversible? |
|---|---|---|
| **bbox** (`geography.json`) | what we ever FETCHED | ⛔ no — outside it was never acquired |
| **polygon** (`nb.polygon`) | what is IN the neighborhood | yes, authored |
| **disc** (`nb.radius`/`boundary`) | how much world we DRAW | yes, authored |

Invariant: **bbox ⊇ disc ⊇ membership.** It held nowhere and was checked nowhere until 2026-07-20 (Księży Młyn committed a radius of 1530 m against a 2.07×1.55 km fetch — 56% of the disc had no data behind it, and two of its four boundary streets had never been pulled).

**⭐ WHAT A NEIGHBORHOOD IS — the definition every requirement here inherits** (Jacob, 2026-07-21):

> *"A neighborhood is a collection of buildings/structures which are connected by people-run accounts. The idea is that a neighborhood can be described by its hard surfaces but it is enlivened by their soft contents."*

The **unit is the structure, not the area.** What makes these buildings one neighborhood is that people run accounts in them; geometry is a **proxy** for that relation, and a proxy fails at the margin — which is why step 5 correction is first-class and never collapses into a rule. It is how a *social* fact overrules a *geometric* guess ("Honorary Hood Residents": one `activate` on Galeria Łódzka carries 22 listings — a structure full of accounts is more a member than an empty one inside the polygon). **Corollary: soft-content loss outranks geometry loss.** A bake that takes listings 84 → 5, or silently drops place cards whose anchor left the baked set (`bake-content.js:554`), is not a content bug — it is the neighborhood dying. *(Supersedes an unconfirmed coordinator guess, "a small world correct at its edges," which had the boundary as the thing being defined.)*

**⭐ THE SELF-TENSING CIRCLE — the boundary isn't everything, but it also is** (Jacob, 2026-07-21: *"we have to determine that polygon to determine who is included… It's a self-tensing circle, for sure. So the boundary isn't everything but it also is."*). ⛔ **Do not resolve this into a hierarchy in either direction** — a coordinator pass first had the boundary as the definition, then over-corrected to "membership is primary, the boundary is downstream." Both are wrong. They **mutually determine**, and the loop settles under tension:

> **polygon → who is included → where the hood's mass actually is → where the disc belongs → how much world we draw around it.**

You cannot skip the polygon to get the members, and you do not know where the hood *is* until you have them.

**⭐ THE DISC IS THE GROUND PLANE — the neighborhood is a planet of its own.** The circle is not merely "what we render"; it is *the fundamental graphical piece*, the ground plane of the map itself. We present the map in a virtual environment where **the horizon is "whatever is outside the neighborhood"** — the hood reads as a small world entire, with its edge as that world's horizon. This is why the **hood centroid and the disc centroid are importantly LINKED**, and why an off-center disc is a *world-breaking* defect rather than a cosmetic one: the planet goes lopsided, horizon crowding one side while content runs off the other. The two centerpoints below are therefore **not independent** — the frame origin may sit anywhere stable, but the disc must be composed against the hood's mass for the world to read as a world.

**⛔ THE ORDERING CONSTRAINT — street names come FROM the fetch.** You cannot name a boundary street before the data containing it has been pulled. So the arc is necessarily **search → fetch generously → author the boundary from what came back**. The search does not know the neighborhood and never did; it only sizes the envelope. Every attempt to reason about the boundary *before* step 3 is reasoning about data that does not exist yet.

**⛔ THE GAZETTEER IS A HINT, NEVER A REQUIREMENT — the INVENTED hood is a first-class case, not an error path.** "Hi-Pointe–DeMun" is two St. Louis areas someone joined; Nominatim has no such place and never will. That is the *normal* condition for any hood a person named — realtor coinages, subdivisions, composites, and the name people actually use for where they live. Śródmieście and Księży Młyn came up in search and made the gazetteer path look like the norm; it is a sample of the easy ones. **The street-selection path must therefore work from zero — no ring, no usable bbox — because it is the primary authoring surface, not a corrector for the gazetteer's answer.**

1. **Search a PLACE.** `geocodePlace` → Nominatim, keeping the bbox **and** the `official` ring. The gate accepts `boundary=*` and `place=neighbourhood|suburb|quarter|borough|city_district|town|village|city` — US neighborhoods are the latter (Park Slope: `place=neighbourhood`, 13-pt polygon, previously discarded). ⛔ **Never any polygon**: "DeMun" falls through to `leisure=park` "DeMun Park", and a park offered as a neighborhood is worse than no answer. `cls`/`kind` ride to the UI so a bad match is visible; a point-match (an address on a 4.9 km street) is flagged rather than silently padded. **For a composite/invented hood the gazetteer returns nothing usable — proceed on the envelope alone.**
2. **The searched place sizes the fetch envelope** — its bbox + `FETCH_MARGIN_M` (1000 m), then **squared about the centre in metres**. Square because the disc is concentric and a circle cannot fit a rectangle narrower than its diameter. The envelope is drawn on the aerial (dashed, outside shrouded) — the aerial is a global tile layer and the fetch is a bounded rectangle, and nothing distinguished them before. **Generous on purpose:** it must contain a hood whose shape is not yet known, so it is sized to be safely too big.
3. **Fetch** — the one irreversible step. OSM + MSBF + parcels, then `skeleton.js --index` → `clean/street-index.json` (welded, named, UNSIMPLIFIED chains + junctions). **Not the skeleton** — that is the First Bake. **⭐ This is the step that produces STREET NAMES** (`GET /:scene/street-names`, corridor-collapsed so a divided arterial reads as one entry) — the vocabulary every later boundary decision is spoken in.
4. **Author the BOUNDARY from those street names.** Three interchangeable entries, all resolving to the same artifact — *a set of named streets*: **(a) click them on the aerial · (b) pulldown · (c) text entry.** Picking on hydrated geometry is preferred (a misspelling or an honorific can't cost you a boundary), but the three are equivalent by design and the operator uses whichever suits the hood. A gazetteer ring, where one exists, is a *starting hint* only: they run from Lafayette Square's coarse 26-pt contributor outline to Księży Młyn's 815-pt cadastral trace that jogs around individual buildings (median segment 9.3 m). Resolving onto street centerlines normalises both — Księży Młyn's 357 vertices become 4 corners at 129 ha — and is what makes "a neighborhood doesn't cut a block in half" true by construction.
   - **The boundary is the street RUNS.** Corners are where consecutive runs meet at a shared junction — a *by-product of the walk, never the method*. The order-dependent corner resolver (`computeExtentCorners`) was excised 2026-07-20 (`55df128a`); do not reintroduce corner-first thinking.
   - **A boundary street is a centerline; the MARGIN is corrected in step 5, by design.** Hi-Pointe–DeMun takes the buildings off the far side of its **southern** street (its four sides: Big Bend Boulevard, Forest Park Parkway, Skinker Boulevard, Clayton Road), expressed as 16 `activate` overrides. ⛔ **Do not invent a per-street "side" property for this** — the correction layer already is the mechanism, and it is *durable*: `building-overrides.json` is written only by `POST /<scene>/building-overrides` and is read-only to `pipeline.js` / `bake-buildings.js`, so **overrides survive a polygon re-derive**. Re-authoring the street borders does **not** cost the 16 picks. *(A 2026-07-21 pass claimed it did and proposed a side property on that basis; both were wrong.)*
5. **Correct — this is a first-class step, not a patch over a missing rule.** Exclusion loops (`BezierPen`) for strips, per-building `activate`/`hide` for the margin ("Honorary Hood Residents": one `activate` on Galeria Łódzka carries 22 listings). A real boundary is a centerline plus a margin judgement, and the margin is the operator's to make — the tool's job is to make that judgement cheap and durable, not to predict it. Both mechanisms persist independently of the polygon (`nb.exclusions`, `building-overrides.json`), so re-authoring the boundary never discards them. *(The known ergonomic gap: the pen carves **exclusion** loops only — `ExtentApp.jsx:1085` holds `exclusionsLL` with no inclusion counterpart — so bringing in a run of far-side frontage is 16 individual clicks rather than one band. That is a gesture to add to the existing mechanism, not a new concept.)*
6. **Bake** — `commit-extent` (origin moves <100 m keep the frame and skip `reproject-raw`) → `skeleton.js` → pour.

**⭐ SHOWN vs ACTIVATED — membership may want to be TRI-STATE, not binary** (Jacob, 2026-07-21 — *new, and he flags it as never previously raised; the excavation will not find it in the corpus*):

> *"Someday I might want to 'show' all buildings within the circle but only 'activate' those within the neighborhood. Practically speaking, that would stamp the building outlines into the slab in whatever color the user determines, but would not extrude and would not be clickable."*

| state | region | treatment |
|---|---|---|
| **activated** | inside the neighborhood (`polygon ∪ activate`) | full — extruded, clickable, carries accounts / place cards |
| **shown** | inside the disc, outside the neighborhood | footprint **stamped flat into the slab** in an operator-chosen colour; **no extrusion, not clickable** |
| **absent** | outside the disc | nothing — beyond the world |

*Coordinator inference, 2026-07-21 — test it, don't inherit it:* this maps exactly onto the definition above. **Activated = hard surface WITH soft contents** (people-run accounts). **Shown = hard surface WITHOUT them** — real fabric, no life, therefore no click, because there is nothing behind it to open. **Absent = past the horizon.** It also serves the planet doctrine directly: today the band between polygon and disc rim is empty ground, so the world ends at a seam and then there is nothing until the horizon. Stamped outlines fill that band with real context, so the neighborhood *thins into* its surroundings rather than stopping dead. Cheap, too — a flat stamp is a fraction of an extrusion's verts, so it may afford a **larger** disc, not a smaller one.

**Precedent, and the gap it exposes:** `neighborhood-membership.mjs` already draws these two regions for **trees and lamps** — but as a **density dissolve**, thinning the population across the ground's own `fade` band. What is described here is **not** a dissolve: every building is kept, at a *reduced representation*. That is a **representation tier assigned by membership region at bake** — the same shape as the tree-LOD doctrine (`project_tree_lod_role_at_bake_not_distance`: role at bake, never a live distance swap). ⚠️ **Buildings do not use the shared module at all** — `pipeline.js` and `bake-buildings.js` carry private copies that know nothing about `fade`/`density`/`keep`, and `pipeline.js` pre-clips the raw input so non-members are *gone* by `map.json`. A shown-tier therefore cannot be expressed today: the data required to draw it is discarded before anything could. **Folding buildings into the shared module is the prerequisite, not the feature.**

> ⚠️ **THE DISSOLVE ITSELF IS UP FOR REVISION — its rationale has expired, and it has no operator surface** (Jacob, 2026-07-21). `neighborhood-membership.mjs` presents the two-region rule as settled and quotes Jacob to authorise it — but the quoted rationale is **`"outside, inside the radius, we watch for GPU"`** (2026-07-15), a **performance concession, not a design principle.** Jacob: *"we've optimized trees and we haven't yet resolved lamps but I don't think we're in the GPU emergency we were before — and irrespective of whether or not we keep this notion, we don't have any access to it through the interface."* Two separate faults:
> 1. **Expired premise.** The thinning exists to protect a GPU budget that trees no longer strain. Whether the greater circle should thin *at all* is now an open aesthetic question, not a settled constraint. **Do not treat the dissolve as doctrine.** (Lamps remain unresolved — that part of the concern is live.)
> 2. **No interface.** There is no operator control over the dissolve, the fade band's effect on population, or (prospectively) the shown-tier colour. Per `feedback_authoring_panel_is_the_formalization_surface`, **a behaviour with no panel is not a formalized feature** — it is a hardcode with a good comment. Whatever survives revision needs a knob.
>
> ⭐ **The general lesson, and it is the one this subsystem keeps paying for:** a requirement can be *live* (never retracted, still quoted, still enforced in code) while its *rationale* is dead. The excluder settlement failed exactly this way. **When auditing this corpus, check whether the REASON still holds — not merely whether the rule was ever revoked.**

**Membership = `(polygon ∪ activate) − (exclusions ∪ hide)`**, the disc being only the fallback when a scene has no polygon. `pipeline.js:246-255` implemented this before any of it could be authored; what was missing was persistence, and two server paths that destroyed a polygon if it appeared.

**⭐ TWO CENTERPOINTS — they are different things and must not be collapsed.** The generous envelope of step 2 and the hood discovered in step 4 do not share a center, and nothing guarantees they ever will:

| | what it is | moves? |
|---|---|---|
| **fetch center** (`geography.json` lat/lon) | the midpoint of the envelope we fetched over; becomes the **frame origin** at commit | ⛔ frozen after commit — moving it runs `reproject-raw`, rebuilds the skeleton, renumbers `segOrd`, and strands the x/z-only tree census (which nothing reprojects) |
| **hood center** (`keptCenter`) | the centroid of the **kept buildings** — where the neighborhood actually is, and what the **disc** (the ground plane / the planet) must be composed against | ✅ free — it is a *value*, not a frame; nothing reprojects against it, so it may be recomputed on every bake at zero cost |

Once membership correctly isolates the hood, the kept buildings are an **off-center cluster** inside the generous envelope. That is expected, not a defect. The disc must be drawn on the **hood center**; the frame must stay on the **fetch center**. ⚠️ **These are separate values but not independent concerns** — the frame origin is arbitrary-but-stable and answers to nothing, while the disc centroid answers to the hood's mass because the disc is the ground plane and its edge is the world's horizon (above). Getting the disc wrong does not merely offend the eye; it breaks the planet. **⭐ D4 — FIXED at the commit path, 2026-07-22 (`d82c5e60`), with one residual.** The defect was that the two centerpoints were *forced equal*: `makeCircleBoundary` hardcoded `center: [0,0]`, so the artifact could not carry a hood center even when one was known. As-built now:

- ✅ **`makeCircleBoundary(radius, center = [0,0])`** (`serve.js:616`) takes a center and generates the 256-gon around it. The **commit** path passes the real one — `makeCircleBoundary(radius, discCenter)` (`serve.js:1455`) — so a commit **freezes the frame origin** *and* **stores the disc off-origin**. Proven with `[65,-40]`.
- ✅ **`CenterHandle.jsx`** (`f0e47916`) mounts the disc centroid as an in-scene draggable dot (`ExtentApp.jsx:1816`), the R10 handle the fix was for.
- ⛔ **RESIDUAL — the light `rescope` path still drops it:** `serve.js:1583` calls `makeCircleBoundary(radius)` with **no center**, so re-scoping a committed hood (the common "adjust the radius and re-Bake" gesture, step 10) silently snaps its disc back to `[0,0]`. That is the mechanism behind an authored off-origin disc reverting to origin. **Fix = pass the stored `prev.center` through the rescope branch.**
- ⛔ **RESIDUAL — the client still short-circuits:** `ExtentApp.jsx:1145` `if (committed) return { x:0, z:0 }`, so `keptCenter` is only live for an *un*-committed scene. The handle can move the disc; the auto-derived hood center is not consulted once committed.

⚠️ Possibly the same root as the **OPEN BUG — 3D Browse framing** below ("too high and slightly to the left"): a disc forced concentric with the origin while the content sits wherever the buildings are.

**⭐ THE IDENTITY LOCK — the seal is the registry (LANDED 2026-07-22, `ca2db7ca` + `8c1b65ae`).** Building identity used to be `msbfId: i` — the fetch **array index** — so any re-fetch renumbered every building and every listing / logo / place card silently re-pointed at the wrong structure. Now `fetch-msbf.js` consults a **per-scene centroid-keyed registry** (`msbf-identity.js`: `loadRegistry` / `assignIds` / `saveRegistry`): a footprint that was seen before **keeps its permanent id**, a new one **appends** off a persisted `highWater` mark, and a dropped one keeps its number **reserved**. Nothing is ever renumbered. Verified: a tight re-fetch took 13,427 → 8,460 footprints with **zero renumbers** (9/9 registry checks green). This is the mechanical guarantee behind "the bb centroid may grow or shrink but never move" — grow/shrink from a fixed center leaves every retained id resolving, which is the whole content safeguard (`EXTENT-DESIGN §3.3/§4`).

> ## ⛔⛔ POURING A SECOND SCENE CLOBBERS LAFAYETTE SQUARE — read this before any pour (2026-07-23)
>
> **This is not a hazard; it happened.** Pouring a `lafayette-square-staging` scene **overwrote production LS's render data** — `src/data/ribbons.json` was re-derived (148k), the LS slab was re-poured, and the looks were rewritten, all without the staging pour ever naming LS. Recovery was `git checkout HEAD --`, and the restore then *silently* came back with trees off (the restored commit carried `layerVis.tree:false`), which took a re-bake to notice. Live site was untouched only because nothing had been pushed.
>
> **The mechanism — LS is not a scene; it is the mold the kit was cast around.** Every other hood lives under `cartograph/data/<scene>/clean/`. **LS's render data lives at the *shared default* paths** — `src/data/{ribbons,buildings,street_lamps,landmarks,park-feature-elev}.json` — **imported by literal name** (verified 2026-07-23: **13 static name-imports across 10 files**; `ribbons.json` alone at 8 sites — `MapLayers.jsx:8`, `CartographApp.jsx:53`, `measureModel.js:16`, `useCartographStore.js:9`, `LafayettePark.jsx:16`, …). So `src/data/*` is simultaneously **"the shared default"** *and* **"LS's own render data."** When a poured scene writes the default, it writes **LS**. LS bleeds into everyone because **LS *is* the fallback.**
>
> **⭐ THE RULE: retire the `src/data/*` name-imports BEFORE a second pour — or every pour clobbers LS.** Site-by-site patching does not close this; the conflation is the root (`EXTENT-DESIGN §2.1`, worklist step 4). Until then, treat any non-LS pour as **destructive to production LS** and check `git status` on `src/data/` + `public/baked/lafayette-square/` immediately after.
>
> **⭐ AND: a restore is not a verification.** `git checkout HEAD --` gives you *a* known state, not the *right* one — it silently carried a toggled-off layer. **"Restored" ≠ "looks right": re-open the scene and use the operator's eye** (`feedback_proxy_render_is_not_the_operator_eye`).

- **New `serve.js` endpoints** (scene-parametric, per the one-pipeline rule): `POST /:scene/fetch-extent` (write `geography.json` from the framed bbox → fetch OSM → **street index**, not the skeleton — `skeleton.js --index`; the skeleton is the First Bake and belongs to Bake), `GET /:scene/street-names` (skeleton-sourced, corridor-collapsed `{major,minor}`, alphabetized), `POST /:scene/street-geom` (highlight a candidate on the aerial), `GET /:scene/skeleton-labels`, `GET|POST /:scene/neighborhood` (draft load/save), `POST /:scene/commit-extent` (re-center `geography.json` to the centroid → `reproject-raw.js` → `skeleton.js` → write `neighborhood_boundary.json` + `neighborhood.json`; park the Designer camera), and **`POST /:scene/pour`** (the one-click build). - **The Pour** (`POST /:scene/pour` + `onPour` in ExtentApp + `pourScene` in `api.js`): `pipeline.js --skip-elevation` (boundary-clipped) → `promote-ribbons.js --scene=<s>` → ensure a Look bound to the scene (`createLook` now forwards `scene`) → `setActiveLook` → `bakeLook(force)` (ground/buildings/lamps/scene/AO) → load fresh ribbons → `setShot('designer')`. **Scene-generic is verified** — `pipeline.js`/`promote-ribbons.js`/the whole bake all run for a non-default scene off its own OSM buildings + land-use (+ STL parcels when in STL); the old bake-route "scene-specific pipeline not yet implemented" comment was conservative. Guarded per-scene (`_seedsInFlight`). It is **long** — the derive processes the whole fetched area *before* the clip, so a wide fetch is both slow and heavy.
- **`pipeline.js` boundary clip** (after `deriveLayers`, before the `map.json` write) — the **data-wall neuter**, a KIT step gated on the scene having a `neighborhood_boundary.json`. Drops features entirely outside `keepR = streetFade.outer + 30` (top-level layer arrays + ribbons faces/tiles/medians/corridors/junctions/nameTransitions, inclusive `touches` test so edge refs survive); **streets/alleys/paths are polyline-CLIPPED, not kept whole** (`clipRun` — trim each polyline to the circle, keep the longest inside run) so an overshooting named boundary arterial (South Big Bend ran 3882 m across a 2502 m hood) can't stick out asymmetrically and skew the content bounds. Result on a wide (~5.4 km) test fetch: `map.json` 180→52 MB, ribbons 22→8 MB, symmetric street bbox. **The 3D ground mesh stays a clean ±1461 disc regardless** — the clip changes the ribbons/content bounds, not the ground.
- **`bake-buildings.js` — render ledger + membership** (KIT). `loadBuildings(scene)` reads a per-scene **render ledger** `data/<scene>/buildings.json` for every scene (LS's is derived from its authored `src/data/buildings.json` via `derive-ls-render-ledger.js` — the `scene==='lafayette-square'` source hardwire retired; LS bakes byte-identical). **Membership = `(polygon ∪ activate) − (exclusions ∪ hide)`** (2026-07-20; the circle is the fallback when a scene has no polygon) (`NEIGHBORHOOD-INPUTS §5.2`) — applied primarily in `pipeline.js` (so `map.json` is the single filtered source the 2D Designer + bake share), re-applied here (`:603-613`) belt-and-suspenders; ⚠️ dropping `nb.polygon` (`24323ab2`) is **retired**. *(Was: the boundary-street polygon; before that, centroid-within-R / any footprint point outside the circle.)*
- **`cartograph/reproject-raw.js` (new)** — recomputes `raw/osm.json` x/z from lon/lat via the *current* `geography.json` (`config.wgs84ToLocal`, `writeIfChanged`): the **re-center-within-bbox** lever, so geography / skeleton / aerial stay aligned after a recenter. Used by `commit-extent`.
- **`api.js` helpers (new):** `pourScene`, `geocodeZip`, `fetchExtent`, `fetchStreetGeom`, `fetchNeighborhood`/`saveNeighborhood`, `commitExtent`, `fetchExtentCorners`, `fetchStreetNames`, `fetchSkeletonLabels`, `fetchOsmLabels`; `createLook` forwards `scene`; `fetchGeography`/`fetchNeighborhood` are cache-busted (`?t=` + `no-store`).

## 9. What this enables

- **A new Look = a new `design.json` (+ a re-baked `ground.json`/`bin` + `scene.json`).** No code changes, no migrations. *(`ground.svg` is no longer the runtime artifact — CLI-only QA now.)*
- **A new helper (Arborist, Park Composer, etc.) = a new directory + a published artifact.** No coupling to existing helpers.
- **A new neighborhood (someday) = new geometry + a new default Look.** The helpers and runtime stay the same.

This is a kit, not a bespoke build. The pattern is the value.
